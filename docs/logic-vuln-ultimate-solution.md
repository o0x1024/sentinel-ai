# 逻辑漏洞与越权漏洞终极方案蓝图

## 1. 目标

本文档描述一套不依赖当前实现细节、以白帽挖洞视角为中心的终极方案，重点针对：

- 逻辑漏洞
- 水平越权
- 垂直越权
- 跨租户越权
- 状态机与流程越权
- LLM / Agent / SaaS / 云厂商场景下的授权边界问题

这套方案的核心目标不是“猜参数名”或“扫接口”，而是：

1. 重建系统中的主体、对象、动作、上下文、状态关系
2. 基于业务边界生成测试假设
3. 以最小化、可控的主动验证方式复现问题
4. 输出高可信、可解释、可复现的漏洞证据

可以压缩成一句话：

`围绕业务边界做假设驱动的主动验证，而不是围绕参数名做被动猜测。`

---

## 2. 第一性原理

越权和大部分逻辑漏洞，本质上都可以抽象成下面这条关系：

`Subject -> Action -> Resource -> Context -> State`

系统需要回答 5 个问题：

1. 谁在操作
2. 对什么对象操作
3. 执行了什么动作
4. 在什么上下文中执行
5. 在当前业务状态下，这个动作本来是否应该被允许

只要这五个维度可以被稳定建模，绝大多数越权和逻辑漏洞都可以统一处理。

---

## 3. 设计原则

### 3.1 总原则

1. 以业务边界为中心，而不是以参数名为中心
2. 以对象关系为中心，而不是以单请求为中心
3. 以行为链路选点，而不是以接口枚举选点
4. 以假设驱动测试，而不是以盲扫驱动测试
5. 以 LLM 做理解与规划，而不是做全执行
6. 以确定性执行和结果判定闭环，而不是以模糊推断闭环
7. 以单账号场景为默认设计起点，多账号是增强项

### 3.2 关键结论

- 单账号水平越权应作为一等公民场景设计
- 多账号对比不是必要前提，只是增强证据
- 对象识别不应停留在 `id/orderId/userId` 词表匹配
- 行为上下文和业务流程，对逻辑漏洞的重要性不低于请求本身

---

## 4. 总体架构

终极方案建议分成 6 层：

1. 数据采集层
2. 业务建模层
3. 语义理解层
4. 假设生成层
5. 主动验证层
6. 证据归因层

逻辑流如下：

```text
用户行为 + 流量 + 页面 + 响应 + 会话上下文
                    ↓
            业务对象与流程建模
                    ↓
            LLM 语义理解与规划
                    ↓
           越权 / 逻辑漏洞假设生成
                    ↓
           主动最小化安全验证执行
                    ↓
            高可信 finding 与证据沉淀
```

---

## 5. 数据采集层

终极方案不能只看 HTTP 流量，至少要同时采 5 类数据：

### 5.1 用户行为序列

- 点击了什么
- 输入了什么
- 从哪个列表进入哪个详情
- 是哪个按钮触发了当前动作
- 页面停留与跳转链路

### 5.2 请求与响应

- 路径、方法、查询参数、请求体
- 状态码、响应体、响应头
- 分页、列表项、对象详情、错误信息
- 异步任务触发和回调

### 5.3 页面上下文

- 页面标题
- 路由
- DOM 中展示的对象编号
- 列表列名
- 表单标签
- 按钮文案

### 5.4 身份与会话上下文

- 当前账号
- 角色
- 租户 / 项目 / 工作区
- session / token / cookie
- 是否代操作、代理身份、子账号

### 5.5 副作用结果

- 是否创建了对象
- 是否状态变化
- 是否触发导出
- 是否触发审批
- 是否发起异步任务
- 是否影响余额 / 库存 / 配额 / 权限

---

## 6. 业务建模层

这层的职责不是存“请求记录”，而是构造业务数字孪生。

### 6.1 核心实体

建议至少有以下实体：

- `Subject`
  - 用户
  - 角色
  - 租户
  - 项目
  - 工作区
  - 服务账号
  - Agent

- `Resource`
  - 订单
  - 图书
  - 报销单
  - 客户
  - 工单
  - 文件
  - 对话
  - 模型
  - 云资源

- `Action`
  - read
  - update
  - delete
  - approve
  - export
  - pay
  - refund
  - invoke

- `Context`
  - 页面
  - 路由
  - 入口
  - 终端类型
  - 环境
  - 时间窗口

- `State`
  - 草稿
  - 提交
  - 审核中
  - 已批准
  - 已支付
  - 已归档

- `Observation`
  - 一次真实观察到的行为单元

- `Hypothesis`
  - 一次待验证的逻辑漏洞假设

- `VerificationRun`
  - 一次主动验证执行记录

### 6.2 目标产物

最终需要构建出业务图谱：

`主体 --对--> 对象 --执行--> 动作 --处于--> 状态 --受限于--> 上下文`

---

## 7. 对象引用识别器

对象检测不能只停留在硬编码字段匹配，而要升级成对象引用识别器。

### 7.1 输入来源

- path 动态片段
- query 参数
- body 顶层字段
- body 嵌套字段
- 数组中的字段
- 响应中的对象
- DOM 中展示的对象标识
- 路由参数
- 下载链接、分享链接、附件链接中的标识

### 7.2 输出语义

每个引用都应尽量标注成更高层类型，例如：

- `resource_id`
- `owner_id`
- `tenant_id`
- `parent_id`
- `child_id`
- `workflow_id`
- `state_id`
- `share_id`
- `conversation_id`

### 7.3 核心要求

1. 递归解析 JSON
2. 支持数组和嵌套对象
3. 同时分析请求和响应
4. 记录字段路径，而不是只记录字段名
5. 建立对象类型和字段路径之间的稳定关系

---

## 8. 行为链重建引擎

逻辑漏洞检测的选点不应以“接口”作为基本单位，而应以“行为链”作为基本单位。

### 8.1 需要识别的高价值链路

- 列表 -> 详情
- 列表 -> 编辑
- 列表 -> 删除
- 列表 -> 导出
- 搜索 -> 打开对象
- 创建 -> 提交 -> 审批
- 详情 -> 支付 / 退款 / 确认
- 查询 -> 下载附件 / 快照 / 报表

### 8.2 行为链的价值

行为链能帮助系统理解：

- 当前操作是不是对象边界敏感动作
- 列表中是否已有可用于替换的对象池
- 当前请求是否是管理员动作入口
- 某个敏感动作是否缺少正常前置步骤

---

## 9. 语义理解层

LLM 在终极方案中是规划器，而不是执行器。

### 9.1 LLM 适合做的事

1. 理解行为序列的业务语义
2. 理解动作语义和高风险边界
3. 判断当前链路更像对象越权、角色越权还是流程越权
4. 生成测试计划和优先级

### 9.2 LLM 不应直接负责的事

1. 直接执行参数替换
2. 直接控制高风险枚举
3. 代替确定性响应比较器
4. 成为唯一漏洞结论来源

### 9.3 LLM 输出应是结构化计划

建议至少包含：

- 是否值得测
- 测哪个请求
- 目标对象是什么
- 应优先替换哪些引用
- 用什么策略
- 为什么值得测
- 风险与停止条件

---

## 10. 假设生成层

检测引擎应统一生成 6 类核心假设：

### 10.1 对象边界假设

- 同类对象是否可互换访问
- 列表中的其他对象是否都可访问
- 自己对象与他人对象是否缺乏隔离

### 10.2 角色边界假设

- 普通用户能否执行管理员动作
- 审批人动作是否能由申请人自己完成
- 低权限是否能读取高敏信息

### 10.3 租户边界假设

- tenantId / projectId / workspaceId 是否可替换
- 跨组织、跨项目、跨区域是否成立

### 10.4 状态边界假设

- 未提交是否能审批
- 未支付是否能退款
- 已完成流程是否能撤回或重开

### 10.5 关系边界假设

- 父子对象是否可错配
- ownerId / assigneeId / reviewerId 是否可替换
- 本对象与关联对象是否可交叉拼接

### 10.6 间接访问假设

- 搜索、导出、附件、快照、预览、日志、通知、异步任务是否泄露未授权对象

---

## 11. 主动验证层

主动验证层是终极方案的核心竞争力。

### 11.1 核心策略库

1. 同类对象替换
2. 列表到详情交叉替换
3. 父子对象错配
4. 所有者字段替换
5. 跳步骤执行
6. 逆序执行
7. 重复执行
8. 并发执行
9. 间接通道验证
10. 受控枚举

### 11.2 重要执行原则

1. 优先替换已观察到的合法对象，不优先盲暴力
2. 优先单步、最小扰动验证
3. 高风险策略必须有限速、限次数、限作用域
4. 对具有副作用的动作必须有安全保护

### 11.3 单账号策略优先级

单账号白帽场景下，优先顺序建议为：

1. 列表中同类对象替换
2. 路径对象替换
3. body / query 对象替换
4. 父子错配
5. 所有者字段替换
6. 受控小范围邻近测试

---

## 12. 多账号增强能力

多账号不是前提，但如果存在，应作为增强证据层：

1. 同对象多身份差分访问
2. 角色阶梯测试
3. 跨租户测试
4. 组、子账号、代理账号继承测试

多账号主要增强：

- 垂直越权
- 跨租户越权
- 复杂组织边界问题

---

## 13. 响应判定层

漏洞判断不能只看状态码。

### 13.1 四层判定

1. 传输层
   - 200 / 403 / 404 / 500 / 302

2. 结构层
   - 是否返回了同类对象结构
   - 是否出现业务字段
   - 是否仍然是成功响应

3. 语义层
   - 返回对象是否发生变化
   - 返回内容是否像真实业务结果
   - 是否只是错误页包了一层 200

4. 副作用层
   - 状态是否变化
   - 对象是否被修改
   - 是否产生导出、任务、通知、账务等结果

### 13.2 高可信证据

高可信越权证据通常表现为：

- 替换对象后仍返回真实对象详情
- 执行敏感动作后业务状态实际改变
- 间接通道返回了未授权资源
- 响应中的所有者 / 租户 / 关联对象发生了可解释变化

---

## 14. 评分与 finding 体系

### 14.1 三维评分

1. 边界强度分
   - 当前动作是否天然高风险

2. 测试证据分
   - 主动验证结果是否形成强证据

3. 业务影响分
   - 涉及隐私、财务、权限、跨租户、核心资产的程度

### 14.2 finding 分级

- `signal`
  - 只有弱信号

- `candidate`
  - 已有清晰测试假设

- `strong_candidate`
  - 主动验证出现明显异常

- `verified`
  - 已形成稳定复现证据

- `critical_verified`
  - 已证实高影响越权或核心逻辑漏洞

### 14.3 证据包要求

每个高质量 finding 至少应包含：

- 基线请求
- 变异请求
- 响应对比
- 对象变化说明
- 状态变化说明
- 风险归因摘要
- 最小复现步骤

最终交付形态不应只是“漏洞列表”，而应是一套逻辑漏洞作战台。

### 15.1 业务地图

展示：

- 主体类型
- 对象类型
- 高风险动作
- 租户 / 角色 / 项目边界

### 15.2 高价值链路面板

自动列出：

- 详情 -> 删除

- 父子与关联关系

### 15.4 测试建议面板

### 15.5 执行控制台

## 18. 一句话总结

这套终极方案的本质不是“找到某个 id 参数并替换它”，而是：

`先理解业务里谁能对什么对象做什么动作，再围绕这些边界自动生成并执行最小化安全验证。`

如果只保留最核心的判断标准：

- 它是否真正理解了对象
- 它是否真正理解了行为链
- 它是否真正理解了授权边界
- 它是否真正能做最小化主动验证
- 它是否真正能给出高可信、可复现证据

满足这五点，才称得上面向白帽的逻辑漏洞与越权漏洞终极方案。

## 19. 第三方评审后的收敛结论

从第三方功能评估和方案评估的角度，当前蓝图方向成立，但如果不做边界收敛，容易变成范围过大、落地周期过长、执行风险偏高的“终局愿景”。

结合评审意见，建议保留并吸收以下收敛结论：

### 19.1 目标边界收敛

当前产品和平台的核心目标应明确为：

`主要面向水平越权的平台或功能模块`

这意味着优先解决：

- 单账号对象边界访问
- 列表到详情对象访问
- 列表到编辑 / 删除 / 导出对象访问
- body / path 中对象替换型水平越权
- 附件 / 预览 / 快照 / 导出等间接对象访问

而不是在同一阶段试图统一解决所有逻辑漏洞、垂直越权、跨租户、复杂状态机和 Agent 权限链问题。

### 19.2 必须保留的风险控制结论

评审后建议明确保留以下结论：

1. 方案范围必须收敛，避免一次性覆盖所有逻辑漏洞
2. 不应在第一阶段构建完整全局业务数字孪生，而应优先构建任务驱动的局部图谱
3. 主动测试必须按风险分层，默认只读优先
4. 单账号场景应作为默认设计起点，但不能夸大其对复杂垂直越权的覆盖能力
5. 所有模块必须支持退化运行，不允许因为行为数据、LLM 或对象识别缺失而整条链路失效
6. 面向白帽的外部产品形态必须收敛，前台只展示高价值入口、测试建议、验证结果和证据包

### 19.3 当前阶段建议聚焦的能力

从收敛角度，建议优先打透如下主线：

1. 行为驱动选点
2. 对象引用识别
3. 单账号对象池
4. 对象替换和交叉替换
5. 只读优先的主动验证
6. 响应差异与对象差异判定

## 20. 对象引用识别器为什么是成败关键

对于面向水平越权的平台而言，对象引用识别器不是附属模块，而是底座能力。

真正的问题不是“找字段名”，而是：

`哪个值代表哪个业务对象，这个值处于什么关系里，是否值得拿来做边界测试。`

### 20.1 对象识别不是字段识别

简单把 `id / orderId / userId` 视为对象键，在真实业务里远远不够。水平越权真正依赖的是：

- 资源对象主键
- 所有者字段
- 父子对象关系
- 关联对象关系
- 访问票据和分享入口

如果系统不能区分这些角色，就会把“可替换资源边界”和“无意义技术字段”混在一起。

### 20.2 难点示例

#### 示例一：同值不同义

```json
{
  "id": "12345",
  "userId": "12345",
  "operatorId": "12345",
  "traceId": "12345"
}
```

这里四个值看起来都像对象键，但实际语义完全不同：

- `id` 可能是订单或图书对象
- `userId` 可能是主体
- `operatorId` 可能只是操作者
- `traceId` 可能根本不是业务对象

如果系统把它们全部当成“可替换对象键”，后续验证会产生大量无效测试。

#### 示例二：不同值同义

同一个图书对象在不同接口里可能表现为：

- `bookId`
- `id`
- `isbn`
- `archiveCode`
- `itemCode`
- `/books/{id}`
- `/inventory/detail?code=xxx`

对白帽来说，这些可能都指向同一对象边界；对系统来说，如果不能把它们归并成“同一对象的不同引用”，对象池就会碎裂，列表对象和详情对象也无法关联。

#### 示例三：对象只在响应或页面里出现

典型链路：

1. 搜索图书
2. 列表响应里出现 `bookCode`
3. 用户点击某一行
4. 详情请求却使用内部主键 `id=879312`

这里的关键不是有没有识别到字段，而是系统是否能理解：

- 列表里的 `bookCode`
- 页面中点击的那一行
- 详情请求里的 `879312`

是否都指向同一个对象。

#### 示例四：对象深藏在嵌套结构里

```json
{
  "query": {
    "book": {
      "baseInfo": {
        "archive": {
          "itemCode": "BK-2024-001"
        }
      }
    }
  },
  "operator": {
    "userId": "u-101"
  }
}
```

如果只看顶层字段，会完全漏掉真正的对象引用。  
如果简单做递归抽取，又会引入大量噪音字段，因此必须同时具备字段路径理解和语义置信度。

#### 示例五：path 动态片段不一定是资源对象

下面这些路径都包含动态值：

- `/books/12345`
- `/tasks/run/12345`
- `/reports/export/202404`
- `/callback/7f8e9a`

但它们分别可能对应：

- 资源 ID
- 任务执行 ID
- 时间窗口
- 回调 token

如果系统把所有动态 path segment 都视为资源对象，就会在主动验证时引入大量误测。

#### 示例六：父子对象错配

```text
/project/100/task/9001
```

这里至少包含：

- 父对象 `project=100`
- 子对象 `task=9001`

真正的水平越权不一定只是替换 `taskId`，还可能是：

- 用自己的 `projectId`
- 搭配别人的 `taskId`

如果对象识别器不理解父子关系，平台只能做到最浅层的 ID 替换，而抓不到更真实的水平越权。

#### 示例七：可见对象与真实授权对象不一致

页面上可能展示：

- 图书编号 `BK-001`

但点击详情时真正请求的是：

- `/detail?id=981273`

这说明前端展示值和后端授权主键并不一致。  
如果平台只会从页面拿可见对象，就无法稳定建立对象池和详情访问边界。

#### 示例八：访问票据不是资源主键

例如：

- 分享码
- 下载 token
- 预览 key
- attachment token

它们在技术上是访问入口，但在业务上不是资源主键。  
如果系统不区分 `resource_id` 和 `access_token`，会把不同类型的漏洞混淆。

### 20.3 结论

对象引用识别器的真正任务不是：

`找到所有像 ID 的字段`

而是：

`找到所有可能影响资源边界的引用，并判断它们属于哪一类对象关系。`

## 21. 修正版对象引用识别方案

在“主要面向水平越权”的收敛前提下，对象引用识别器建议采用三层结构。

### 21.1 第一层：强确定性对象候选层

只识别最稳定、最值得信任的对象候选：

- path 中高置信动态资源段
- query / body 中高置信资源字段
- 列表响应中的主键列
- 详情响应中的主键
- 点击行为后立即传播到请求中的关键值

要求：

- 高 precision
- 宁可少，不可乱
- 低置信度对象不进入高风险主动测试

### 21.2 第二层：关系补全层

在强确定性候选之上建立对象关系：

- 父对象 / 子对象
- 列表对象 / 详情对象
- 所有者 / 操作者
- 资源主键 / 访问票据
- 同一对象的别名字段

这一层可以利用：

- 同值传播
- 请求与响应相关性
- 页面点击与请求时间邻近
- 字段路径模式
- 列表列与详情字段相似性

### 21.3 第三层：LLM 辅助语义归一层

当前两层无法确定时，再让 LLM 介入，主要做：

- 这更像资源键还是所有者键
- 这是对象主键还是分享票据
- 当前详情请求最可能对应列表里的哪类对象
- 哪个字段最值得拿来做水平越权测试

LLM 在这里是“裁判”和“归一器”，而不是对象识别的唯一来源。

### 21.4 三层结构的目的

这样设计的目的不是追求“理解所有业务”，而是确保：

1. 对象池可靠
2. 交叉替换稳定
3. 父子错配可做
4. 低价值字段不会污染主动验证

## 22. 修正版实施主线

结合评审结论，当前版本最合理的主线应为：

1. 行为链选点
   - 列表 -> 详情
   - 列表 -> 编辑
   - 列表 -> 删除
   - 列表 -> 导出
   - 搜索 -> 对象详情

2. 对象识别三层结构
   - 强确定性候选
   - 关系补全
   - LLM 归一

3. 单账号对象池
   - 列表中出现过的对象
   - 响应中出现过的对象
   - 详情链路中的对象
   - 关联资源对象

4. 主动验证
   - 同类替换
   - 父子错配
   - 所有者替换
   - 附件 / 导出 / 预览 / 快照的间接访问

5. 安全边界
   - 默认只读优先
   - 高风险动作需要人工确认
   - 暴破和受控枚举仅作为最后策略

这条主线比“全能逻辑漏洞平台”更稳，更适合作为面向水平越权的第一阶段终局方案。

## 23. 安全中心信息架构：漏洞台账 + 安全工作台

在产品形态上，前文提到的“白帽工作台”不应只停留在抽象概念上，最终应落成 Security Center 中的真实功能区域。

但它也不应直接替代现有漏洞列表页。  
更合理的结构是：

`漏洞台账负责收敛结果，安全工作台负责展开调查过程。`

### 23.1 为什么不能只继续堆在漏洞 Tab

漏洞 Tab 的天然职责是：

- 展示 finding 列表
- 提供筛选、排序、保存视图
- 查看基础详情
- 查看证据
- 查看时间线
- 进行基础状态流转

这类界面本质上偏“结果视图”。

而安全工作台要承载的是：

- 请求链
- 行为链
- 对象池
- 对象关系
- 测试计划
- 执行记录
- 基线与变异差异
- 人工备注与复盘结论

这类界面本质上偏“过程视图”。

如果继续把工作台能力全部堆进漏洞 Tab，会产生几个直接问题：

1. 列表页和详情页重新变得臃肿
2. SQLi、RCE、SSRF 等普通漏洞被逻辑漏洞专属信息淹没
3. 调查过程和漏洞台账混杂，信息密度失控
4. 后续复盘、实验记录、执行日志很难组织

因此，最合理的形态不是继续把所有能力塞进漏洞 Tab，而是在 Security Center 内新增一个“安全工作台”层。

### 23.2 为什么也不应完全另起一个独立系统

虽然安全工作台应独立于漏洞 Tab，但它不应成为和漏洞中心完全平行、彼此割裂的系统。

否则会出现：

- finding 和 case 双重维护
- 状态、标签、证据分裂
- 用户在两个系统之间来回跳转
- 逻辑漏洞和其它漏洞来源无法统一复盘

正确关系应是：

- 漏洞台账是统一收口层
- 安全工作台是统一调查层
- 两者通过 finding / case 强绑定

即：

- 从漏洞台账进入安全工作台
- 在安全工作台里完成调查、验证、复盘
- 再把结论回写到漏洞台账

### 23.3 两层结构的职责边界

#### 漏洞台账

负责：

- finding 列表
- 筛选与保存视图
- 严重级别与状态
- 基础详情
- 证据摘要
- 时间线摘要
- 快速验证入口
- 导出与评测快照

它回答的问题是：

- 有哪些漏洞
- 当前状态是什么
- 严重级别是什么
- 证据大致是什么
- 生命周期走到了哪一步

#### 安全工作台

负责：

- 调查过程
- 复盘过程
- 验证执行过程
- 结论沉淀

它回答的问题是：

- 为什么怀疑这里有问题
- 当时观察到了哪些链路
- 做了哪些替换和验证
- 哪一步确认了它成立或不成立
- 后续应该如何处理和沉淀

### 23.4 安全工作台应服务哪些漏洞

安全工作台不应只服务逻辑漏洞。

它应服务所有来源的 finding，包括但不限于：

- 逻辑漏洞
- 水平越权
- 垂直越权
- SQLi
- SSRF
- RCE
- 敏感信息泄露
- LLM / Agent 安全问题

不同类型漏洞在工作台中展示的信息密度可以不同：

- 逻辑漏洞额外强调行为链、对象关系、验证计划
- SQLi / SSRF / RCE 更强调请求上下文、payload、响应回显、利用链

但底层工作台能力应统一：

- 可观测
- 可追溯
- 可复盘

### 23.5 推荐的信息架构

建议 Security Center 最终分成两层：

1. `漏洞`
   - 统一漏洞台账

2. `安全工作台`
   - 统一调查与复盘空间

两层之间通过 `finding -> case/workbench session` 关联。

推荐交互方式：

- 在漏洞详情中提供 `进入工作台`
- 在工作台中支持 `回写状态 / 标签 / 结论 / 摘要`

这样既能保留现有漏洞中心的收敛能力，也能引入真正面向调查与复盘的工作区。

### 23.6 安全工作台的第一阶段最小版本

第一阶段不需要做成完整“作战平台”，建议先实现 4 个核心面板。

#### 1. 案件概览

展示：

- finding 标题
- 来源
- 当前状态
- 当前结论
- 负责人
- 最近一次验证动作

作用：

- 用一个稳定入口承接“这个问题现在调查到哪一步”

#### 2. 请求与证据链

展示：

- 基线请求
- 关联请求
- 相关证据
- 时间线串联

作用：

- 把零散证据组织成一条可阅读的链

#### 3. 验证与对比

展示：

- 基线请求与响应
- 变异请求与响应
- 差异点
- 执行记录
- 当前验证结果

作用：

- 让“成立 / 不成立”变成基于对比的过程，而不是一句结论

#### 4. 复盘记录

展示：

- 人工备注
- 判断依据
- 误报原因
- 复现步骤
- 后续建议

作用：

- 把一次漏洞调查沉淀成团队资产

### 23.7 第二阶段扩展能力

在第一阶段稳定后，再扩展以下能力：

- 行为链视图
- 对象池视图
- 对象关系图
- 自动测试计划视图
- 同类 case 聚类
- 历史实验回放
- 调查模板与知识沉淀

### 23.8 产品决策结论

最终结论如下：

1. “白帽工作台”必须最终落成真实功能页面或功能区域，而不是只保留抽象概念
2. 现有漏洞 Tab 继续保留，作为统一漏洞台账
3. 安全工作台应作为 Security Center 中独立的第二层，而不是继续塞进漏洞 Tab
4. 两者必须打通，而不是各自独立
5. 第一阶段优先实现“案件概览 + 请求与证据链 + 验证与对比 + 复盘记录”四个核心面板

一句话总结：

`漏洞台账负责看结果，安全工作台负责看过程。`

## 24. 安全工作台实施稿

本节把前述“漏洞台账 + 安全工作台”进一步落成可实施方案，覆盖：

- 页面信息架构

- 第一阶段页面字段清单

目标不是一次做成最终作战平台，而是先形成一条稳定、可演进的实现路径。

### 24.1 页面信息架构

建议在 Security Center 下形成如下结构：

```text
Security Center
├── 漏洞
│   ├── 列表
│   ├── 漏洞详情
│   └── 从详情进入安全工作台
└── 安全工作台
    ├── 案件列表
    ├── 案件详情
    │   ├── 案件概览
    │   ├── 请求与证据链
    │   ├── 验证与对比
    │   └── 复盘记录
    └── 从案件回写 finding
```

#### 页面职责

`漏洞`

- 面向所有 finding 的统一台账
- 更偏浏览、筛选、汇总、状态流转

`安全工作台`

- 面向调查、验证、复盘的案件空间
- 更偏链路组织、测试对比、结论沉淀

#### 推荐用户路径

1. 用户在漏洞列表中发现值得深入分析的 finding
2. 在漏洞详情页点击 `进入工作台`
3. 系统创建或打开与该 finding 绑定的 case
4. 用户在工作台中完成调查、验证、复盘
5. 工作台将结论回写 finding 的状态、标签、摘要和证据

### 24.2 第一阶段页面结构

第一阶段建议只做 2 个主页面：

1. `案件列表`
2. `案件详情`

#### 案件列表

主要用途：

- 查看当前正在调查或需要复盘的案件
- 按负责人、状态、来源、漏洞类型筛选
- 快速进入调查现场

#### 案件详情

采用四面板结构：

1. 案件概览
2. 请求与证据链
3. 验证与对比
4. 复盘记录

## 26. 数据模型：finding 到 workbench case

工作台不应直接替代 finding，而应在 finding 之上新增一个“案件层”。

### 26.1 核心关系

建议关系为：

`一个 finding 可以关联一个或多个 case session`

其中：

- finding 是漏洞台账中的正式对象
- case 是调查与复盘对象
- case session 是一次具体调查过程

如果第一阶段要简化，可以退化成：

`一个 finding 对应一个主 case`

### 26.2 建议核心模型

#### WorkbenchCase

用于表达“这个 finding 在工作台中的调查实体”。

建议字段：

- `case_id`
- `finding_id`
- `title`
- `status`
  - new
  - investigating
  - awaiting_verification
  - verified
  - false_positive
  - archived
- `owner`
- `assignee`
- `current_conclusion`
- `priority`
- `created_at`
- `updated_at`
- `last_activity_at`

#### WorkbenchSession

用于表达“一次具体的调查/验证过程”。

建议字段：

- `session_id`
- `case_id`
- `started_by`
- `started_at`
- `ended_at`
- `entry_source`
  - finding_detail
  - manual
  - system_agent
  - replay_result
- `summary`

#### WorkbenchEvidenceLink

用于把工作台和原始证据打通。

建议字段：

- `link_id`
- `case_id`
- `evidence_id`
- `role`
  - baseline
  - related
  - generated
  - verification

#### WorkbenchVerificationRun

用于记录工作台中的每次验证动作。

建议字段：

- `run_id`
- `case_id`
- `strategy`
- `baseline_request_id`
- `mutated_request_snapshot`
- `result`
- `result_summary`
- `started_at`
- `completed_at`
- `operator`

#### WorkbenchNote

用于沉淀人工判断与复盘内容。

建议字段：

- `note_id`
- `case_id`
- `author`
- `kind`
  - observation
  - conclusion
  - false_positive_reason
  - remediation_note
  - replay_note
- `body`
- `created_at`

### 26.3 与 finding 的同步边界

工作台不应复制所有 finding 字段，而应只维护调查态信息。

推荐同步方式：

- finding 仍然是事实源：
  - title
  - severity
  - vuln_type
  - status
  - evidence

- case 维护调查态：
  - owner
  - current_conclusion
  - investigation status
  - notes
  - verification runs

回写时仅更新 finding 中少数关键字段：

- 状态
- 摘要
- 标签
- 验证结果摘要

## 27. 第一阶段页面字段清单

下面给出第一阶段四个核心面板的字段建议。

### 27.1 案件概览

建议展示：

- case 标题
- 关联 finding 标题
- finding 类型
- 严重级别
- 当前案件状态
- 当前调查结论
- 负责人 / 最近更新人
- 来源
- 首次发现 / 最后发现 / 最近活动时间
- 当前是否已有验证结果

推荐操作：

- 回到漏洞详情
- 改变案件状态
- 指派负责人
- 进入验证面板

### 27.2 请求与证据链

建议展示：

- 基线请求卡
- 关联请求列表
- 原始 evidence 列表
- 时间顺序串联
- 每条请求与 case 的关系
  - baseline
  - related
  - supporting
  - generated

推荐操作：

- 设为基线请求
- 标记关键证据
- 从请求进入验证计划

### 27.3 验证与对比

建议展示：

- 当前验证策略
- 基线请求与响应
- 变异请求与响应
- 请求差异
- 响应差异
- 状态差异
- 对象差异
- 验证结论
- 每次执行记录

推荐操作：

- 重跑一次
- 切换验证策略
- 接受当前结论
- 标记误测

### 27.4 复盘记录

建议展示：

- 观察记录
- 结论记录
- 误报原因
- 复现步骤
- 后续建议
- 修复建议

推荐操作：

- 新增备注
- 固定为最终结论
- 同步回 finding 摘要

## 28. 第一阶段最小交互流

建议第一阶段先打通下面这条最小闭环：

1. 用户在漏洞详情页点击 `进入工作台`
2. 系统创建或打开与该 finding 绑定的 case
3. 案件概览自动展示 finding 基本信息
4. 请求与证据链自动导入 finding 关联 evidence
5. 用户在验证与对比中查看已有基线与验证结果
6. 用户填写复盘记录
7. 用户将结论回写 finding

这条链路一旦成立，就已经具备：

- 可观测
- 可追溯
- 可复盘

之后再逐步叠加：

- 行为链
- 对象池
- 自动测试计划
- 同类 case 聚类

## 29. 实施优先级建议

从交付风险和收益比来看，建议顺序如下：

### P0

- `finding -> case` 绑定
- 安全工作台入口
- 案件概览
- 请求与证据链
- 复盘记录

### P1

- 验证与对比面板
- 验证执行记录
- case 状态与负责人
- finding 回写

### P2

- 行为链视图
- 对象池视图
- 对象关系图
- 自动测试建议

### P3

- 同类 case 聚类
- 案件模板
- 调查知识沉淀
- 团队协作与评论

## 30. 实施结论

如果按第一性原理评估，“漏洞台账 + 安全工作台”是合理的结构分层：

- 台账承载结果
- 工作台承载过程

而从工程角度，第一阶段最关键的不是做多智能，而是先建立：

1. finding 到 case 的稳定绑定
2. 证据链的可阅读组织
3. 验证结果的可对比呈现
4. 复盘结论的可沉淀与可回写

只要这 4 点成立，安全工作台就已经从概念变成可落地产品。
