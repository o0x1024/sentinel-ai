Assistant UI Refactor Concepts

AI 助手消息块重构参考，先把信息结构拉清楚，再决定视觉语言。

这页不是单纯换皮，而是围绕消息块的第一性问题来拆：用户需要先看见什么，工具执行感要不要前置，引用和下一步动作要不要显式，长对话里垂直密度怎么控。下面四套方案分别对应四种产品取向，方便你判断要偏“会话体验”还是偏“分析工作台”。

信息优先级 先决定标题、状态、正文、引用、工具回执谁先被看到，视觉层级才有依据。
执行感设计 AI 消息不是纯文本块，它通常包含思考、调用、证据和后续动作。
长对话可读性 样式要能扛几十轮排查，而不是只在单条消息截图里好看。

四套方向

01 Signal Rail 左侧状态轨突出“正在执行”和“已完成”。适合工具调用频繁的助手。
02 Command Deck 暗色控制台卡面，更强操作氛围。适合安全分析、终端代理、系统监控。
03 Review Ledger 偏审阅工单，把风险、证据、建议动作拆开看。适合审计和报告场景。
04 Compact Thread 高密度消息流，弱化装饰。适合长会话、排障、多轮追问。
Concept 01

Signal Rail

这套把“消息块”当作一次执行单元，不只是正文容器。左侧色轨持续提醒当前阶段，适合模型会频繁暴露 reasoning、tool call、tool result 的场景。

适合: 工具型助手 优点: 状态明确 风险: 视觉占比偏强

为什么成立

用户真正要理解的是这条回复现在处于什么阶段，而不是只看一大段字。状态轨把执行感直接嵌进消息块。

建议落地点

注意点

如果每条消息都上色轨，视觉疲劳会比较快。建议只给 AI 主回复和运行态消息启用。

Concept 02

Command Deck

这套明显更像分析控制台。主消息块保留对话属性，但把工具回执、代码片段、操作按钮全部压到同一张卡内，适合安全助手、系统代理、终端集成类界面。

适合: 安全/终端代理 优点: 氛围强 风险: 不适合轻聊天

适用建议

为什么成立

当消息内容本身就是“操作指令 + 代码 + 工具回执”时，暗色卡面会比传统聊天气泡更稳。

建议落地点

可以只在开发者模式、系统代理、工作流执行页启用，不必覆盖所有聊天入口。

注意点

如果主产品整体是明亮主题，这套更适合作为局部嵌套面板，而不是整页风格反转。

Concept 03

Review Ledger

这套把 AI 回复当作“审阅条目”而不是聊天泡泡。核心思路是把风险判断、证据、建议动作拆开放，让用户扫一眼就知道结论、依据、下一步分别是什么。

适合: 审计/报告 优点: 可扫读 风险: 聊天感较弱

适用建议

为什么成立

用户经常不是想“继续聊天”，而是想把 AI 输出转成一个可执行的判断条目。这套结构天然更适合。

建议落地点

适合漏洞分析、RAG 证据归纳、审计报告草稿、任务结论页。

注意点

如果所有消息都这样排，会显得太重。适合只用于高价值回复或“生成结论”模式。

Concept 04

Compact Thread

这套优先解决长对话的密度问题。保留角色、状态、结果摘要，但把边框、头像、留白都压缩。适合一屏要看很多轮上下文的场景。

适合: 长对话排障 优点: 高密度 风险: 仪式感较弱

适用建议

为什么成立

消息块真正的稀缺资源是一屏可见上下文。高密度方案会直接提升排障节奏，尤其是多轮问答。

建议落地点

适合默认聊天流，另外可以把“重点回答”升级成更重的卡片样式，形成轻重配合。

注意点

因为装饰被削弱，所以要特别注意标题、状态、按钮文案的语义准确性。

Recommendation

如果你要落到当前 Sentinel 项目里

从现有组件结构看，当前项目已经有 `message block + tool panel + markdown` 的基础，最稳的路径不是推倒重做，而是先收敛消息信息架构，再替换视觉壳子。

优先建议 先试 `Signal Rail + Compact Thread` 混合版，保留执行感，同时不牺牲长对话密度。
高价值增强 把工具调用、证据引用、下一步动作从“附属区块”提升为 AI 回复中的一等元素。
不建议 不要单纯只改圆角、边框和背景色。那不会解决“消息块到底承载什么”的问题。
